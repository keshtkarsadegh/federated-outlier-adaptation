# P19 - the selected configurations at 20% dropout

`jobs/v4/d01_p19_drop20.txt` - **20 tasks**, 100 rounds each.

## The question

Every method comparison in `Digits_study01` was made at **9 of 10** clients per
round - one participation point. This runs the same configurations on the same
cohort at **8 of 10**, so the pair is a controlled comparison of the dropout rate
with the methods held fixed:

| point | drawn | where it comes from |
|---|---|---|
| 10% dropout | 9 of 10 | the existing P15 / P09 runs |
| **20% dropout** | **8 of 10** | **this file** |

**Varied:** the number of clients drawn per round. **Held:** the cohort, the
fold book, the old-data book, g-0 as initialisation and as anchor and teacher,
the local budget (5 epochs, batch 64), the horizon (100 rounds), the uniform
policy, and the three evaluation categories. Nothing else moves.

## The participation rule

```
participants(n, d) = floor((1 - d) * n)
```

```
floor((1 - 0.2) * 10) = 8
```

One expression serves every stage this programme has run - 9 of 10 here, 16 of
20 in the earlier programme, 4 of 5 at the small-federation stage, 8 of 10 at
this dropout point. It lives in
`training/study_config.py:participants`, every emitter calls it, and no task
file carries a literal, so a stage cannot drift from the rule with nothing in
the output to say so. `study_config` asserts at import that the study's own
`clients_per_round` still equals `participants(10, 0.1)`.

The float is guarded: `(1 - 0.8) * 10` is `1.9999999999999996` in IEEE754, and a
bare floor of it is 1 where the arithmetic says 2. Over every federation size to
100 and every whole-percent rate there are **56** such cases, each of which would
silently train one client fewer than the rate says. The guard repairs all 56 and
manufactures none - swept and asserted in the tests.

**The extreme cases are the one documented exception.** At two clients the rule
keeps one, and dropping a client from a two-client federation is not a
participation study but a coin flip on whether the round happens; at one client
it keeps nobody. Those cases run at full participation - `--policy all
--participation 1.0` - which is what the extreme emitter already states in the
line itself, and `participants` refuses those sizes by name rather than quietly
rounding up.

## What the trimmed mean does at 8 participants

The winner's server rule is `trimmed_0p4`, which drops `int(f * K)` from each end
of the ordered coordinate:

| f | K = 9 (the 10% point) | K = 8 (this file) |
|---|---|---|
| 0.1 | trim 0 -> 9 survive (not a trimmed mean at all) | trim 0 -> 8 survive |
| 0.2 | trim 1 -> 7 survive | trim 1 -> 6 survive |
| 0.3 | trim 2 -> 5 survive | trim 2 -> 4 survive |
| **0.4** | trim 3 -> **3 survive** | trim 3 -> **2 survive** |

`trimmed_0p4` discards three from each end at both points, so it now keeps 2 of 8
rather than 3 of 9 - a quarter of the round instead of a third. That is a change
in the rule's own severity riding along with the dropout, and it has to be read
alongside the number rather than after it. The table is generated by
`five_cells.trim_survivors`, which is the server's own `int(f * K)` expression,
and each cell is checked in the tests against the real `con_delta_trimmed_mean`
on a poisoned-ends vector.

## The four configurations

| # | id | family | aggregation | penalty |
|---|----|--------|-------------|---------|
| 1 | `winner` | concurrent | `trimmed_0p4` | `feature_l2_lam0p1` |
| 2 | `balanced` | concurrent | `anchor_0p03` | `ntd_b0p01_t0p5` |
| 3 | `sequential` | sequential | `seq_order_shuffle` | `feature_l2_lam0p01` |
| 4 | `control` | **both** | plain `fedavg` | none |

The same four as P18, so the two stages are comparable to each other as well as
to the 10% point. Each of the first three names one aggregation rule, which lives
in exactly one family, so a task produces one result; the emitter refuses a pair
the cross did not actually run (checked against
`tables/p15_combination_grid.json`) and refuses a rule reported on a schedule it
does not belong to.

**Why the control is here.** Without an unmodified baseline a change between the
two dropout points could not be attributed: every selected configuration might
move together simply because fewer clients trained. It runs `BaseTrainer` with
`--aggregation fedavg` and no penalty, which covers **both** schedules in the one
task, as every plain-FedAvg line of this study does.

4 configurations x 5 folds = **20 tasks**.

## The cohort and the book

The full `cohort10` - all ten writers, unchanged - and
`fold_books/cohort10.foldbook.npz`. Twenty percent dropout is about the *draw*,
not about the population, so there is no narrowing here and no new book. The
emitter asserts the cohort file holds exactly ten clients and that the book
covers every one of them.

## Cost

Measured from this study's own completed arrays at 100 rounds: P14 reg-full
(m=9, both families) 209 s mean; P15 combos (m=9, one family) 115 s; P16 extreme
(m~1.3, one family) 53 s. A one-family task costs about `42 + 8.1 m` seconds, so
~107 s at m=8, and the both-family control ~1.8x that, ~193 s.

```
15 x 107 s  +  5 x 193 s  =  ~2,570 s  =  ~0.7 GPU-h
```

Budget 1 GPU-h. The 4-hour per-task limit in `study_phase.sbatch` is ample.
